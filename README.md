В статье Sansec рассматривается критическая связка уязвимостей в самом движке PHP — **PHP2Shell (CVE-2026-109618 и CVE-2026-109619)** с рейтингом опасности **9.2 из 10 (CVSS v4.0)**.

---

## 1. Анализ статьи Sansec: в чем суть угрозы

* **Что это такое:** Две ошибки класса *Use-After-Free* (использование памяти после ее освобождения) в ядре PHP. Они возникают, когда запрос вызывает фатальную ошибку (чаще всего нехватку памяти — Out-of-Memory при превышении `memory_limit`) во время парсинга данных до того, как PHP успевает корректно очистить структуры в памяти. Следующий запрос к тому же воркеру обращается к этой освобожденной памяти как к валидным данным.
* **Чем грозит:**
1. **Удаленное выполнение кода (Unauthenticated RCE):** Злоумышленник может выполнить произвольный код на сервере без авторизации, просто отправив специально сформированный `multipart/form-data` запрос. Уязвимость срабатывает **до запуска кода самой CMS или фреймворка** (даже если сайт переведен в режим обслуживания внутри WordPress, Magento, Laravel или Bitrix).
2. **Утечка памяти (аналог Heartbleed):** Уязвимость CVE-2026-109618 позволяет через обработчик `session.upload_progress` возвращать куски оперативной памяти воркера обратно клиенту в заголовке куки `PHPSESSID`. В этой памяти могут находиться пароли, API-ключи, сессии других пользователей и приватные TLS-ключи.


* **Какие версии уязвимы:** Все версии от **PHP 5.4 до 8.5.11** включительно (включая PHP-FPM, Apache `mod_php`, LiteSpeed и FrankenPHP).
* **Безопасные (исправленные) версии:** Патчи выпущены для веток **8.5.12, 8.4.27, 8.3.36 и 8.2.35**. Официальной поддержки для PHP 8.1 и ниже от разработчиков PHP больше нет (но мейнтейнеры Ubuntu/Debian и репозитория `ondrej/php` выпускают бэкпорты патчей безопасности).

## 2. Как проверить версию PHP (до и после обновления)

На сервере важно проверять **две** вещи: версию в консоли (CLI) и версию, которую реально использует веб-сервер (PHP-FPM / Apache), так как они могут отличаться.

1. **Проверка версии CLI и установленных пакетов:**
```bash
php -v

```


Чтобы увидеть **все** установленные версии и пакеты PHP в системе Ubuntu (так как их может стоять несколько параллельно):
```bash
dpkg -l | grep -E "php[0-9]\.[0-9]-fpm|php[0-9]\.[0-9]-cli|libapache2-mod-php"

```


*Проверка:* Обратите внимание на точную подверсию во втором столбце (например, `8.3.36-...` или наличие суффикса патча безопасности от Ubuntu).
2. **Проверка активных процессов веб-сервера (PHP-FPM):**
Даже если пакет обновился, старый процесс в памяти может продолжать работать до перезапуска. Проверьте запущенные сервисы и их версии:
```bash
systemctl list-units --type=service --state=running | grep php

```


Затем запросите версию напрямую у конкретного бинарника FPM (подставьте вашу версию вместо `8.3`):
```bash
/usr/sbin/php-fpm8.3 -v

```


*Проверка:* Вывод должен показывать пропатченную версию (`8.2.35+`, `8.3.36+`, `8.4.27+` или `8.5.12+`).

## 3. Что делать с серверами на Ubuntu: обновление и защита

### Шаг А. Обновление PHP до безопасной версии

1. **Обновите списки пакетов и сам PHP:**
Если вы используете стандартные репозитории Ubuntu или PPA `ondrej/php` (стандарт де-факто для свежих версий PHP на Ubuntu):
```bash
sudo apt update
sudo apt --only-upgrade install "php*" -y

```


*Проверка:* Убедитесь, что пакеты скачались и установились без ошибок.
2. **Перезапустите веб-сервер и все пулы PHP-FPM:**
Для PHP-FPM (укажите вашу версию):
```bash
sudo systemctl restart php8.3-fpm

```


Если используется Apache с `mod_php`:
```bash
sudo systemctl restart apache2

```


*Проверка:* Выполните `sudo systemctl status php8.3-fpm` и убедитесь, что время запуска (`Active: active (running) since...`) изменилось на текущую минуту.
3. **Проверьте сервер на следы взлома (Webshells):**
Поскольку атаки начались сразу после публикации информации об уязвимости, проверьте директории сайтов на наличие недавно созданных или измененных `.php` файлов (начиная с 20 октября 2026):
```bash
find /var/www -name "*.php" -newermt "2026-10-20" -ls

```


*Проверка:* В списке не должно быть незнакомых файлов со случайными именами в папках загрузок (`uploads`, `pub/media`, `bitrix/tmp` и т.д.).

### Шаг Б. Временная защита (если обновить PHP прямо сейчас нельзя)

Если на сервере крутится старый проект (например, на PHP 7.4/8.1 без патчей) и обновить его мгновенно невозможно, Sansec и CERT-EU рекомендуют применить экстренные меры:

1. **Отключите `session.upload_progress` и снимите лимит памяти в PHP-FPM:**
Откройте конфигурацию пула (например, `/etc/php/8.3/fpm/pool.d/www.conf`) и добавьте в конец файла:
```ini
php_admin_flag[session.upload_progress.enabled] = off
php_admin_value[memory_limit] = -1

```


*(Примечание: `memory_limit = -1` отключает принудительное прерывание по памяти, которое вызывает баг CVE-2026-109618, но требует контроля за потреблением ОЗУ на сервере. Для PHP 8.5 также добавьте `php_admin_flag[fatal_error_backtraces] = off`).*
2. **Заблокируйте `multipart/form-data` на уровне Nginx/Apache (если сайту не нужна загрузка файлов):**
В блоке `server` в конфигурации **Nginx** добавьте перед передачей запросов в PHP:
```nginx
if ($http_content_type ~* "multipart/form-data") {
    return 403;
}

```


Затем проверьте и перезагрузите конфиг: `sudo nginx -t && sudo systemctl reload nginx`. *(Внимание: это временно отключит загрузку файлов и картинок на сайте, а также некоторые формы чекаута — снимите ограничение сразу после патча PHP).*

## 4. Как обновить PHP в изолированном окружении (`venv` / `phpenv` / Conda)

В отличие от Python, у самого PHP нет встроенного модуля `venv`, поэтому под «PHP в venv» на серверах обычно подразумевается один из четырех вариантов. Чтобы точно понять, какой инструмент управляет этим окружением, активируйте его (или перейдите в папку проекта) и выполните:

```bash
which php

```

В зависимости от того, какой путь покажет команда, примените соответствующий способ обновления:

### Вариант 1: Окружение `conda` / `mamba` (путь вида `.../miniconda3/envs/myenv/bin/php`)

Если PHP установлен как пакет внутри виртуального окружения Conda:

1. Активируйте окружение и обновите PHP через канал `conda-forge`:
```bash
conda activate имя_окружения
conda update -c conda-forge php

```


2. *Проверка:* Выполните `php -v` внутри активированного окружения.

### Вариант 2: Инструмент `php-venv`, `phpenv` или `asdf` (путь вида `~/.phpenv/...` или `~/.asdf/...`)

Эти менеджеры версий компилируют свой отдельный бинарник PHP из исходников в домашнюю или проектную папку:

1. Обновите список доступных версий и установите новую версию ветки:
* **Для `phpenv`:**
```bash
cd ~/.phpenv/plugins/php-build && git pull
phpenv install 8.3.36
phpenv global 8.3.36

```


* **Для `asdf`:**
```bash
asdf plugin update php
asdf install php 8.3.36
asdf global php 8.3.36

```




2. *Проверка:* Перезапустите терминал (или выполните `phpenv rehash`) и проверьте `php -v`.

### Вариант 3: Python `venv` вызывает системный PHP (путь `/usr/bin/php`)

Очень часто на сервере развернут Python-проект в `venv`, который внутри скриптов вызывает `php` для вспомогательных задач.

* Если `which php` даже при активном `(venv)` показывает `/usr/bin/php`, значит, **отдельного PHP внутри `venv` нет** — он использует системный бинарник Ubuntu.
* В этом случае достаточно просто обновить системный PHP через `sudo apt update && sudo apt upgrade` (как описано в разделе 3), и внутри `venv` он обновится автоматически.

### Вариант 4: Изолированный chroot / Jail (например, ISPmanager, CloudLinux CageFS, Plesk)

Если для каждого пользователя на сервере создано изолированное виртуальное окружение файловой системы (chroot/CageFS), где лежат копии `/bin/php`:

1. Сначала обновите системные пакеты PHP на хост-машине (`apt upgrade`).
2. Затем принудительно синхронизируйте виртуальные окружения пользователей:
* Для **CageFS**: `sudo cagefsctl --force-update`
* Для **chroot-окружений панелей управления**: пересоберите chroot в настройках шелл-доступа пользователя или скопируйте обновленные бинарники в jail-директорию.
